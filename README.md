# ВсеЯСветная Грамота — Буковник 147

Исследовательский справочник по заявляемой системе «ВсеЯСветной Грамоты».

## Что является источником истины

`data/bukovy.json` — канонический каталог проекта. Сейчас в нём **68 подтверждённых опубликованных карточек с изображением/описанием**. Источник заявляет 147 Буков; оставшиеся **79 позиций не заполняются догадками** и ведутся отдельно в контуре восстановления.

## Архитектура

Главная единица интерфейса и API — **Букова**.

- `data/bukovy.json` — источник истины.
- `api/v1/bukovy-summary.json` — быстрый каталог для клиентов.
- `api/v1/bukovy-profiles.json` — полный bulk API.
- `api/v1/bukovy/{entry_id}.json` — профиль одной Буковы.
- `api/v1/bukovy-manifest.json` — стабильный список профилей.
- `api/v1/recovery.json` — исследовательское состояние восстановления 147-позиционного массива; кандидаты не являются каноническими позициями.
- `api/v1/recovery.schema.json` — схема recovery API.
- `data/practice/*` — практические записи и истории.
- `index.html` — клиент API; подробные блоки загружаются по требованию.

Истории практиков — ключевой исследовательский слой проекта: для каждой истории в первую очередь фиксируются **действие**, затем **сообщённый результат**, условия применения, уровень свидетельства и источник. Повторяющиеся действия/результаты можно сравнивать только там, где источник позволяет связать их с конкретной Буковой или составным ставом. Практические записи и истории не являются независимым подтверждением эффективности.

## Статусы и доказательность

- `local-copy` — исходное опубликованное изображение сохранено локально.
- `external-or-missing` — локальной копии изображения пока нет; сейчас это относится к **Фите**.
- `candidate` / `secondary-description` — вторичное свидетельство для восстановления; не является канонической записью.
- Практические и эзотерические эффекты приводятся как **утверждения источников/свидетельства**, а не как установленные научные факты.

### Разделение «смысла», «заявленного применения» и истории

Проект не смешивает три разных типа материала:

1. **«Что означает» / смысловая трактовка** — фиксируется как описание или интерпретация источника. Это не считается практическим применением и не превращается автоматически в рекомендацию.
2. **«Её можно применять для…» / явно заявленное применение** — может быть занесено как *заявленное применение*, если источник прямо сообщает, для чего автор/практик предлагает использовать Букову. Это допустимый исследовательский материал даже без отдельной истории результата, но он помечается как заявление источника.
3. **Практическая история** — требует конкретного человека/участника, конкретной Буковы или става, описанного действия и отдельно сообщённого результата/наблюдения. Именно такие записи попадают в `practitioner-histories.json`.

Поэтому формулировки вроде «означает», «связывается с», «показывает» и «можно применять для» не отбрасываются. Они просто получают разные типы доказательности и не подменяют друг друга.

## Проверки

`scripts/validate-bukovy.py` проверяет IDs, порядок и количество карточек, source-image numbers, coverage, API-синхронизацию, профили, manifest и быстрый summary.

GitHub Actions автоматически пересобирает производный API, фиксирует его в `main`, запускает валидацию и публикует GitHub Pages одним конвейером. Это устраняет рассинхронизацию canonical data ↔ API и лишние отдельные workflow-запуски.

## Автономный контур системы

Развитие проекта выполняется как единая система: исследование, развитие тулбокса, управление ветками, публикация статусных поверхностей, самопроверка и накопление эксплуатационного опыта связаны между собой.

- dev — рабочий канон автоматического развития; main — опубликованный стабильный результат.
- Все процессы, записывающие общее состояние dev, используют общий контур сериализации, чтобы не перетирать изменения друг друга.
- scripts/system_self_check.py выполняет периодическую проверку целостности и ограниченный безопасный ремонт.
- data/research/system-health.json — последнее состояние целостности.
- data/research/system-experience.json — дедуплицируемая эксплуатационная память о сбоях, наблюдениях и ремонтах.
- data/research/system-contract.json — машинно-читаемый контракт целостности системы.
- docs/AUTONOMY.md — подробное описание правил автономного развития, восстановления и публикации.
- Статусная страница содержит статическую заглушку на случай неисправности интерактивной части и отдельный self-heal контур.

Правило системы: обнаружить → локализовать → безопасно исправить → проверить → описать → сохранить опыт → продолжить. Неоднозначные и разрушительные изменения не применяются вслепую.
