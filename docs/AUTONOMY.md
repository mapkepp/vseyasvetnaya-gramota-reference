# Автономная система: целостность, ремонт и накопление опыта

## Каноническая модель

Система разделена на защищённые канонические данные, производные представления и автоматические процессы.

- `main` — опубликованный стабильный результат.
- `dev` — рабочий канон автоматического развития.
- Временные и исторические ветки не являются источником истины.
- Производные JSON/API/статусные поверхности должны быть воспроизводимыми из канона.
- Неоднозначные изменения не применяются автоматически.

## Единый контур изменений

Любой процесс, который пишет в `dev`, входит в общую группу `dev-state-writers`. Это предотвращает одновременную запись нескольких workflow в одно рабочее состояние. GitHub Actions поддерживает общие concurrency-группы между workflow, поэтому один общий ключ используется намеренно.

Внутренняя исследовательская параллельность при этом не запрещается: параллельно работают агенты внутри одного цикла, а запись общего состояния сериализуется.

## Самопроверка

`scripts/system_self_check.py` каждые 10 минут проверяет:

1. JSON-состояния;
2. синтаксис Python;
3. JavaScript статусной страницы;
4. наличие статической заглушки;
5. сериализацию всех writer-workflow;
6. наличие статусного реестра.

Безопасные производные данные могут быть пересобраны автоматически. Для неоднозначных или потенциально разрушительных изменений система фиксирует проблему и не делает слепого исправления.

## Статусная страница без намеренного простоя

`research-status.html` содержит независимую статическую заглушку. Если интерактивный JavaScript не работает, информация о восстановлении всё равно остаётся доступной.

Дополнительно `.github/workflows/status-self-heal.yml` периодически проверяет страницу `main`. При повреждении он заменяет её минимальной рабочей страницей восстановления. Это не заменяет полноценный ремонт: после восстановления основная страница должна быть возвращена валидным состоянием.

## Связность описаний

При добавлении новой автоматически публикуемой JSON-поверхности `scripts/sync_status_surfaces.py` обнаруживает её и добавляет в реестр. Статусная страница читает реестр, поэтому новые состояния не должны требовать ручного перечисления в HTML.

## Опыт системы

`data/research/system-experience.json` — ограниченная память эксплуатации. В неё попадают повторяемые наблюдения, ошибки и выполненные ремонты. Одинаковые события дедуплицируются, хранится последние 200 событий.

Это эксплуатационный опыт, а не каноническое исследовательское содержание: он не подменяет источники и не меняет научную/исследовательскую доказательность.

## Правило безопасного ремонта

Автоматический ремонт действует по принципу:

**обнаружить → локализовать → исправить только известным безопасным способом → проверить → записать результат → продолжить работу.**

Если безопасного исправления нет, система не маскирует проблему: она публикует состояние `REPAIR_NEEDED`, сохраняет причину и оставляет решение для следующего специализированного цикла/человеческой проверки.

## Изменение системы

Каждое новое средство автоматизации должно одновременно иметь:

- код;
- workflow/точку запуска;
- источник состояния;
- запись в реестре поверхностей, если состояние предназначено для отображения;
- проверку;
- документацию;
- механизм восстановления или явное объяснение, почему автоматический ремонт запрещён;
- запись эксплуатационного опыта.

## Безопасное перестроение main

Никогда не используется схема «просто заменить main содержимым dev». Текущая архитектура сохраняет обе линии развития и собирает проверяемый кандидат:

1. `main` остаётся опубликованным production-каноном.
2. Перед продвижением создаётся неизменяемая точка восстановления текущего `main`.
3. Текущие `main` и `dev` объединяются в `rebuild-main-candidate`.
4. Кандидат проверяется без изменения `main`.
5. Только после явного подтверждения кандидат продвигается через Pull Request.
6. После продвижения выполняется повторная проверка.
7. При необходимости rollback подготавливается отдельной веткой от сохранённого snapshot и также проходит через Pull Request; принудительная перезапись `main` не используется.

Постоянно существует `main-backup` как быстро доступная копия последнего известного состояния и отдельные immutable snapshot перед продвижением. История `dev` не выбрасывается при сборке кандидата: если изменения конфликтуют, процесс останавливается на конфликте, а не удаляет прогресс.

Критерий готовности: кандидат чистый, проверен, имеет зафиксированный SHA, создан PR, а точка восстановления сохранена. Поэтому после команды «ОК» не требуется заново придумывать процедуру релиза — остаётся только пройти уже подготовленный promotion-контур.

## Публикация

Публикационный workflow должен рассматриваться как часть системы, а не отдельный ручной процесс. GitHub Actions позволяет запускать workflows по push/schedule/manual events; деплой также можно ограничивать concurrency, чтобы не допускать одновременных публикаций.


## Правило зрелости функций

Доказавшая стабильную работу функция становится активной по умолчанию, но не становится необратимой. Для каждой функции сохраняются: состояние, зрелость, проверяемое назначение, способ отключения, путь восстановления и история изменений. Сначала функцию можно отключить без удаления её истории; физическое удаление допускается только после проверки замены и сохранения восстановимого состояния.

Источник текущего реестра: `data/research/feature-registry.json`.

Это означает: **доказано → включено → наблюдается → при необходимости отключается → история сохраняется → восстановление остаётся возможным**.
